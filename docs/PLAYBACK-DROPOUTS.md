# 缺粮为零时的闪断排查

## 0.1.4：根据实测缺帧记录补充传输保护与分类

2026-10-31 收到 0.1.3 真机文本诊断：48 kHz 音源累计补偿 **5088 帧 / 18 次**，
即 106 ms 缺失时间；音源/输出缺粮均为 0，溢出、限幅均为 0。
音源重置仅 1 次，原因为首次接入；采样时网络缓冲约 144 / 150 ms。
输出为响应优先的 30 ms 应用队列，不能把此记录当成稳定模式的对照数据。
手动标记部分文本在音源 JSON 中途截断，缺少末尾事件，无法将某一次缺口准确
对应到用户听见的那次闪断。最近半秒没有近静音也不能排除此前缺口。

已确认接收时间线发生过缺帧并补偿，但旧诊断没有包序号证据，尚不能单独区分
发送采集缺口、发送失败、UDP 丢失和迟到。不能据此断言耳机或 Android 输出故障。
5088 帧恰为默认 96 帧包的 53 倍，只是与整包丢失相符，不是网络根因证明。
总接收计数即时读取，而音源快照每约 80 ms 更新，二者不同步；不能用两者的
包数差直接推算丢包数。原始附件和设备/IP 标识未写入仓库。

发送端现在默认对原始 v1 数据包在约 20 ms 后备份一次，头部和 PCM 完全相同。
不等待备份再发原包、不扩大缓冲、不改变采样率或有损压缩；48 kHz 默认分包的
UDP 负载约由 404 kB/s 增至 808 kB/s。`send` / `tone` 均可通过
`--repair-ms 0` 关闭，范围 0–50 ms。保留现有 150 ms 网络缓冲作对照，
默认 20 ms 备份建议网络缓冲至少 70 ms，留出调度和重排余量。
备份仅在发送工作线程处理，队列上限 128，过期备份跳过，发送会话重同步时清空。
接收端已处理的最近 512 包和待排序包参与去重，不重播、不把已识别副本算作迟到。
普通重排包与补回的备份无法仅凭同一个 v1 包区分，因此 UI 明示“含乱序”。

| 新字段 | 含义与边界 |
| --- | --- |
| `missing_datagrams` / `transport_gap_frames` | 重排截止后仍缺少的序号数量及该区间缺帧；也可能是发送 socket 失败，或同时存在发送缺口，不能直接称为 Wi-Fi 丢包 |
| `sender_gap_frames` | 相邻播放包序号连续、帧位置却跳过的时间，说明发送时间线省略了样本 |
| `unknown_gap_frames` | 序号倒退/重复等无法可靠分类的缺口，避免误报巨大包损失 |
| `gap_filled_packets` | 收到当前等待位置的包并解除队头缺口的次数，可能来自乱序或备份，不是所有备份包的计数 |
| `duplicate_packets` | 已识别的重复包数，正常备份会增加它，不是故障计数 |
| `last_loss_kind` / `last_loss_frames` / `last_loss_age_ms` | 最近已补偿缺口的类型、长度、距音源快照的毫秒数；没有缺口时 age 为 null |

分类与去重累计对同一来源保留至整个接收会话结束，发送会话/采样率/超时重置
不清空累计证据；槽位换来源时清空。分类按排序后的音频时间线做，支持 seq 回绕。
发送端另外报告原包发送失败、备份失败、采集队列丢帧、分包尾部丢帧和重同步。
复制诊断把当前来源、闪断标记和事件放在设备能力列表之前，省略未使用槽位的
电平，降低粘贴截断丢失关键数据的概率；不改变运行中的原始快照。

验证：**49 项 Rust 测试、18 项 Kotlin 测试、格式和严格 Clippy 通过**。
真实 `-Xcheck:jni` / UDP 测试补回 3 个丢失原包、去重 126 个副本，
检查的连续非零 PCM 中最长近静音为 0 帧；关闭修复的 700 帧缺包实验仍留下
597 帧近静音且缺粮为零，证明没有通过隐藏计数来消除问题。

`python scripts/test_redundancy.py --bin-dir dist/windows-x64-0.1.4` 使用实际
sender、UDP 丢包代理和无声 receiver 进程，注入两组各 3 个连续原包丢失：
关闭备份记录 6 包 / 576 帧补偿，开启备份后补回 6 包、补偿 0 帧；
1490 个副本逐字节一致，测得间隔中位数约 21.63 ms。
这是真实本机 UDP 验证，不是用户 Wi-Fi/Android/蓝牙真机试听。
网络长时间中断、两份都丢、超过重排期限、发送采集缺失仍会触发原补偿策略。

覆盖安装 0.1.4 并替换 Windows 发送端，原有 `send --to ...` 命令即可。
先保留 150 ms / 稳定优先；若继续闪断，标记后复制诊断，并附发送端最近一行
计数。若缺少原包且备份也失败，继续查发送和网络；若所有缺帧、重建、近静音
均无对应变化，再检查下游输出。**用户这次闪断的最终根因仍待新实测确认。**

## 0.1.3 的调查背景与验证

2026-10-31，用户反馈 0.1.2 的响应优先和稳定优先都出现闪断，但没有初版的
沙沙声；音源缺粮和输出缺粮均为 0。0.1.1 曾得到用户的稳定播放确认。

本轮所附文件仍为此前录屏，大小 3,359,050 字节，修改时间为
2026-10-31 01:01:10（Asia/Shanghai）。它不能作为 0.1.2 新问题的录音证据。
未操作用户手机，也未在实体 Android 设备复现本次闪断。

## 已确认的代码问题与可重复现象

1. 0.1.2 在重复路由通知中再次调用缓冲设置。新回归测试显示原代码会在
   10 次无变化通知中重复设置；修复后不重复调用。
2. 若设备最初将请求的 60 ms 钳制到 100 ms，原代码不记住实际接受值。
   后续通知不再强制钳制时，会回到 60 ms。测试在原实现失败，修复后保留
   100 ms 安全值。此为策略回归测试，不代表已证实用户耳机发生了相同钳制。
3. 缺粮为零不能排除网络缺帧。实际 JVM/JNI 和 UDP 实验故意跳过 5 包、
   共 700 帧。48 kHz 输出出现 **597 帧（约 12.44 ms）的近静音**，
   混音器缺粮仍为 **0**，新累计补偿诊断正确记录 700 帧、1 次。
   随后更换发送会话，补偿记录仍保留，重置原因变为 `sender_session`。
   这是宿主机的真实 PCM/JNI 实验，没有 AudioTrack，未测实体耳机声音。
4. 旧版在任意输出列表变化和同采样率路由变化时也会重建整个接收端，
   清空来源缓冲和会话计数。代码路径已确认；用户是否遭遇了该重建仍无日志证明。

因此尚不能确认本次主因在网络或播放链路。不能将“两个零”解释为它们都正常，
也不能仅凭上一版调整了输出缓冲就断言一定是 Android 驱动。

## 0.1.3 的修复与对照条件

- 默认稳定优先，保留系统播放缓冲，使用约 10 ms 音频块。
- 兼容基线同样保留系统缓冲，恢复 0.1.1 的固定 1024 帧渲染/写入块；
  仍包含本轮诊断和路由修复，并非完整回退所有应用代码。
- 均衡和响应优先保留为试验模式；它们记住实际接受的缓冲下限，避免无变化重设。
- 首次运行本策略版本时将保存的模式改为稳定优先一次，其他设置保留。
- 路由通知等待 200 ms 确认，忽略重复与暂时为空的路由。同采样率变化交给
  AudioTrack 路由，不重建 JNI/UDP；自动输出采样率确实改变时仍需重建。
- 无关设备列表变化只刷新界面。原手选输出消失时，明确记录并重建到系统默认。
- 写入线程只采样数值指标并发出小型快照，文本格式化移到主线程。
  PCM 静音扫描复用已有数组，不改变样本。

Rust 网络重排截止时间、补帧策略、音质处理和网络缓冲目标未修改；
网络端只增加观测字段及测试。Windows 发送端无需替换。

## 新诊断与判读

“复制诊断信息”现在包含原始音源 JSON、时间戳、当前播放报告、最近一次
手动闪断标记和最近 64 条事件。历史跨接收重建保留，仅在当前 Activity 内存中，
不自动保存文件或上传。复制及标记均由用户点击触发。

| 记录 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 累计补偿帧和次数增加 | 接收时间线缺帧并执行了补偿 | 不能单独区分发送采集丢帧、UDP 丢包或超过重排截止 |
| 音源重置增加及原因 | 会话、格式、超时、重连或时间线跳变使来源重置 | 初次连接也计数，不是每次都异常 |
| 接收会话结束/启动 | 应用确实重建接收端；旧输出计数会被重置 | 不能把新会话的零当作此前没有故障 |
| 写入前近静音段 | 渲染 PCM 中存在至少 2 ms 的近静音，短于 UI 刷新也可留痕 | 原曲停顿、静音和开播等待同样可能触发 |
| 最大写入/渲染间隔 | 调度或阻塞写入的耗时观测 | 正常阻塞写入也可能较长，不等同于断音 |
| 缺粮仍为零且没有补偿/重置/PCM 静音 | 应继续对照兼容基线和输出路径 | 不能证明下游蓝牙或设备一直连续播放 |

本次统计窗与生命周期的静音计数分开显示，以免开播时较长的静音掩盖短暂变化。
标记记录的是用户点击时最近获得的状态，不是准确的声音发生时间；还应考虑
网络和输出缓冲造成的时间差。计时器没有被用来强行节拍或丢弃 PCM。
