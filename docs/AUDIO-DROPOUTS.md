# 0.1.1 断音诊断与修复

2026-10-31，针对 Windows `send` → Android → 蓝牙输出中的沙沙声与闪断进行排查。
用户确认电脑本地播放正常。个人录屏及提取的音轨仅在本机分析，不提交到仓库。

## 录屏能确认什么

- 39.47 秒录屏的 AAC 单声道音轨中，约 18.870 秒和 28.470 秒各有约 6 毫秒的近静音段，按每 1ms RMS 低于 −65 dBFS 检出。这是声轨分析结果，不能单凭它区分原始音乐停顿与软件缺音，也不能把所有沙沙声都归为同一原因。
- 开头一个旧接收会话显示来源缺粮 47 次、丢失 384 帧、队列溢出 0、削波 0；随后录屏中的会话重新开始，显示来源缺粮 1 次。这些是会话累计值，47 次并非发生在这段录屏内。
- 输出区域显示 48kHz / 双声道 PCM float，AudioTrack 缺粮计数为 0。来源缺粮和硬件输出缺粮属于两层，后者为 0 并不表示前者没有缺音。

这些证据优先指向来源缓冲与到达节奏，尚不能排除采集端、无线链路或蓝牙端的其他问题。

## 已复现的问题

`batched_delivery_stops_repeatedly_starving_after_buffer_adapts` 使用真实 SPSC
队列、重采样与混音器，模拟 8kHz 来源每 120ms 成批交付、输出每 10ms
索取音频。没有任何丢包。旧固定 70ms 策略在 12 秒模拟时间内缺粮 100 次，
预热后的 10 秒还在继续缺粮。

另一处问题是网络重排始终只等 12ms，与设置的缓冲大小脱节。
因此即使配置了足够缓冲，迟到 30ms 的包仍可能先被静音替代。

## 改动

1. 缺粮后，每路缓冲目标增加 50%，最少增加 20ms，上限 400ms；会话或采样率重置时恢复设置的初始目标。不会为了压延迟主动缩回小缓冲。
2. 预填充至少覆盖一次完整输出请求及重采样前瞻，避免刚开播就在同一次请求中耗尽。
3. 缺粮后清除旧的时钟速率修正，让新的缓冲目标重新建立。
4. 网络缺包等待采用当前目标减 30ms 的余量，限制在 12–200ms，保留真实缺包的有界静音补偿。它仍有截止时间，无法恢复已经永久丢失的音频。
5. 新安装的图形接收端默认初始缓冲提高至 150ms。已有设置保留。
6. Android 顶部和来源卡片显示实际缓冲、目标和来源缺粮次数；桌面端及无声测试 JSON 也提供相应诊断。

## 验证与复测

同一 12 秒模拟中，新策略预热阶段缺粮 2 次，自动升至 157ms，之后 10 秒
没有新增缺粮。30ms 重排测试无误判丢帧，真正缺包仍在截止后补偿。
另有缓冲上限与会话重置、完整请求预填充、无分配渲染、时钟漂移测试。

本机通过 `cargo fmt --all -- --check`、严格 Clippy、工作区 **41 项测试**，
以及真实 JVM `-Xcheck:jni` 的 UDP、渲染、控制和诊断检查。Android ARM64 /
ARMv7 库与 APK 重新构建并通过 lint。物理手机上的声音改善仍需复测。

升级 0.1.1 APK 后，将初始缓冲设置为 **150ms**，保持原来的 `send` 命令播放
同一段音乐。观察来源 `underruns` 是否继续增加，以及实际缓冲是否频繁归零。
如果声音仍异常但来源缺粮、丢帧、削波和 AudioTrack 缺粮都不增加，应继续比较
手机扬声器/有线与蓝牙输出，并检查 Windows 采集到的 PCM，而非继续盲目加缓冲。
